1. Introduction

Objectives: Demonstrate genuine software engineering ability through construction, auditing, and reconstruction of real software projects as independent deterministic computational models. This presentation is intended for technical evaluation.

Engineering approach: Every demonstration is based on actual source code from the original projects. Algorithms, data structures, rules, and processing pipelines are identified from the source code and reconstructed as independent models that accept configurable inputs and produce reproducible outputs.

Selection methodology: Projects were evaluated on technical depth, algorithmic complexity, implementation quality, originality, completeness, reproducibility, and educational value. Four projects were selected for interactive demonstrations; all discovered projects are documented in this PDF catalog.

Scope limitations: Demonstrations do not execute original projects, do not require specific hardware, external services, or API keys. Some functionality depends on unavailable hardware or services and is documented as such.

3. Architecture and Implementation

For each demonstrated project, the architecture discovered in the source code is detailed: component responsibilities, data structures, algorithms, processing pipelines, internal interfaces, dependencies, design decisions, and technical trade-offs.

3.1 Wi-Fi Time Machine

Architecture: Scanning layer (3 backends: iwd, nmcli, iw-cache) → pure parsers → deduplication by BSSID → SQLite storage → aggregation queries → terminal rendering.

Data structures: ScanResult (BSSID, SSID, channel, frequency, signal, security), stored in tables networks, observations, sessions.

Algorithms: Parsing BSS blocks from iw scan dump, nmcli escaped tokenizer (handling \\: and \\\\), frequency-to-channel 802.11 mapping (2.4/5/6 GHz), security inference from AKM suites, networks × time-bucket heatmap.

Processing pipeline: Scan → parse → dedup (strongest signal) → register in SQLite → aggregation by network/channel → render heatmap, sparkline, bars.

3.2 BLE Radar

Architecture: Scanners (bleak/demo/replay) → Observation → RadarEngine (state machine + EMA) → snapshot → radar frame geometry (cell grid) → curses UI.

Data structures: Observation (address, name, RSSI, timestamp), DeviceState (RSSI EMA, state, trails), DeviceSnap (angle, band, state, jitter).

Algorithms: State machine appeared→active→fading→disappeared (15s/30s windows), EMA RSSI (α=0.4), RSSI strength bands (strong≥-40 … weak), stable angle from SHA-256(address), aspect-corrected polar geometry for radar, replay cursor with seek/speed.

3.3 Process Ecosystem Monitor

Architecture: /proc collector → pure parsers → EcosystemState (lifecycle, CPU, memory, tree) → renderer/UI.

Data structures: ProcessSnapshot (pid, ppid, comm, state, utime, stime, starttime, RSS), ProcessState (lifecycle, CPU%, history rings), SystemSample (system CPU, RAM, load).

Algorithms: CPU% from jiffie delta normalized per-core, identity (pid, starttime) with PID reuse detection, tree from ppid with orphan re-homing via graveyard (max 512), lifecycle new→active/idle→dying→dead.

3.4 Terminal Generative Engine

Architecture: Stateless splitmix64 RNG → seed-derived parameters → render modes (flowfield/plasma/attractor) → framebuffer → half-block encoding → output.

Algorithms: Analytic sine field (flowfield), closed-form color fields (plasma), Clifford/Dejong strange map with coefficient probing (attractor), density accumulation with log+gamma tone curve.

Computational Complexity

  • WTM: O(n) parsing over scan text; O(n) aggregation; O(n × buckets) timeline. Linear in observations.
  • BLE: O(n) ingestion over observations; O(d) snapshot over devices; O(cells + devices × trails) frame.
  • PEM: O(p) update per tick over processes; O(p) tree build; graveyard-bounded ancestor walk.
  • GenArt: O(pixels) per frame flowfield/plasma, O(1) seek; O(iterates × frames) attractor density.

5. Deterministic Reconstruction Methodology

Why independent models: Demonstrations do not execute original projects. This avoids dependencies on hardware (Bluetooth/Wi-Fi adapters), external services, specific runtimes, and API keys. Each model is an independent implementation that reproduces the documented computational behavior of the original.

Source code analysis methodology: 1) Complete inspection of source code structure; 2) Identification of algorithms, data structures, and rules; 3) Extraction of pure functions (no I/O); 4) Reimplementation in TypeScript as independent deterministic model; 5) Documentation of simplifications and assumptions; 6) Validation with automated tests.

Fidelity classification: Level 4 = direct algorithmic reproduction (same logic, only I/O boundary adapted). All 4 demonstrated models are Level 4.

Reproducibility strategy: Same input → same output. Configurable seeds for demo data. Configurable epoch clock. Byte-identical outputs across runs.

6. Individual Computational Experiments

Each demonstrated project includes at least one detailed experiment with configurable inputs, processing steps, intermediate results, and final outputs. Interactive demonstrations are available in the web application showcase/.

6.1 Wi-Fi Time Machine — Baseline Experiment

Input: Synthetic iw dump fixture with 3 APs (Home-Network on ch1, Office-5G on ch36, Six-G on 6 GHz ch1).

Steps: 1) Parse 4 BSS blocks → 4 observations; 2) Deduplication (Home-Network appears 2×, keep −45 dBm) → 3 networks; 3) Per-network aggregation (first/last seen, times seen, avg/best signal); 4) Per-channel statistics; 5) Time heatmap; 6) Signal sparkline; 7) JSON/CSV export with SHA-256 sanitization.

Reproducible output: 3 networks detected, 3 observations, channel 1: 1 obs, channel 36: 1 obs, channel 1 (6 GHz): 1 obs. Sparkline: ▁▄▆█ (signal −45 to −70 dBm).

6.2 BLE Radar — Baseline Experiment

Input: 8 synthetic demo devices with seed 7, 30 simulated seconds.

Steps: 1) Generate observations with RSSI random walk and lifecycles; 2) Ingest into RadarEngine (state machine + EMA); 3) Snapshot at time t (visible devices); 4) Radar frame geometry (strength rings, sweep, markers); 5) Lifecycle summary.

Reproducible output: With seed 7 and 30 s: visible devices vary between 5-8; states: appeared/active/fading; RSSI rings mapped to strength (not distance). Deterministic fingerprint: same seed → same frame.

6.3 Process Ecosystem Monitor — Baseline Experiment

Input: 6 synthetic process snapshots (systemd, kthreadd, dbus, browser, renderer + system with 80% CPU, 50% RAM).

Steps: 1) Parse /proc/[pid]/stat (comm with nested parens); 2) Identity (pid, starttime) → spawn 6 processes; 3) CPU% from jiffie delta; 4) Process tree from ppid; 5) System metrics (80% CPU, 50% RAM); 6) History entry.

Reproducible output: 6 living processes, systemd as root (ppid=0), kthreadd as kernel thread (ppid=0 excluded from roots), browser as child of dbus. System CPU: 80%.

6.4 Terminal Generative Engine — Baseline Experiment

Input: Seed 12345, flowfield mode, 100×40 cell canvas, frame 0.

Steps: 1) Parameter resolution from seed (particles, steps, drift, zoom, gain, harmonics); 2) Framebuffer creation; 3) Rendering analytic sine field with drifting particles; 4) Brightness accumulation + tone curve + palette mapping; 5) World fingerprint.

Reproducible output: Flowfield frame with accumulated brightness ribbon. Fingerprint: deterministic hash of (mode, frame, params, pixels). Same seed → same fingerprint.

9. Limitations and Future Development

  • Implemented: 4 deterministic models with tests, web application with 6 sections, bilingual PDF report, bilingual portfolio.
  • Incomplete: Generative engine has 5 failing tests in the original project (not reproduced in model).
  • Simulated: All radio hardware (BLE, Wi-Fi) and /proc are replaced by synthetic inputs in demonstrations.
  • Not available without hardware/services: Real BLE scanning via bleak/BlueZ, real Wi-Fi scanning via iw/nmcli, real /proc reads, persistent SQLite storage.
  • Not verified: Execution on real hardware of original projects (requires specific adapters and permissions).
  • Future improvements: CI pipeline, more scanning backends, GIF/PNG export for GenArt, property-based tests.

Appendix A — Glossary

  • RSSI: Received Signal Strength Indicator — received signal strength in dBm. A strength measure, not distance.
  • EMA: Exponential Moving Average — exponential moving average for smoothing noisy signals.
  • Jiffies: Linux kernel time units (CLK_TCK = 100 by default on x86).
  • PID reuse: Reuse of process identifiers when a PID is freed and reassigned to another process.
  • AKM: Authentication Key Management — authentication suites in Wi-Fi security (PSK, SAE, OWE).
  • Half-block encoding: Terminal encoding where each cell represents 2 vertical pixels (character ▀ or █).
  • Splitmix64: 64-bit mixing function for deterministic stateless random number generation.
